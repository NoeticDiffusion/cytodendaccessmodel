# E021 — Scaling and Motif Generalization

## Purpose

Test whether the branch-accessibility mechanism survives beyond the canonical four-branch / two-trace setup.

E017 established trace export.
E018 established comparator discrimination under canonical parameters.
E019 established one-at-a-time robustness.
E019R locked signature definitions.
E020 established two-parameter robustness regions.

E021 now asks:

```text
Does the slow structural-writing mechanism generalize beyond a hand-built
four-branch, two-trace overlap motif?
```

This is the next major reviewer-facing test against the “toy model” criticism.

---

## Core research question

Does replay-dependent slow branch-level writing still produce a meaningful joint profile when varying:

```text
branch count
trace count
overlap topology
allocation sparsity
hub-like versus chain-like overlap
```

Primary endpoint:

```text
generalized joint profile survives across motifs
```

Secondary endpoints:

```text
linking specificity
false-linking rate
overlap-branch structural advantage
trace-pair linking gain
perturbation sensitivity
rescue selectivity
```

# E021A — Generalized Motif Engine

## Purpose

Create a reusable motif/allocation generator before running scaling experiments.

Implement a small module, for example:

```text

```

or similar.

It should generate:

```text

overlap_map
expected_linked_pairs

target_branches_for_damage
target_branches_for_rescue

```

---

## Required motifs

Implement at least these:

### 1. canonical

The existing four-branch / two-trace motif.

Purpose: reproduce E017–E020.

### 2. weak_overlap

Two traces share one branch weakly.

Expected: linking should be weak or fail below the overlap threshold identified in E020.

### 3. strong_overlap

Two traces share one branch strongly.

Expected: should reproduce canonical-like linking.

### 4. chain_overlap

Trace 1 overlaps with trace 2, trace 2 overlaps with trace 3, but trace 1 and trace 3 do not directly overlap.

Expected: local linking should exceed distant linking.

### 5. hub_overlap

Several traces share one high-use branch.

Expected: strong linking but increased false-linking risk.

### 6. sparse_random

Random sparse allocation matrix with controlled overlap density.

Expected: linking should scale with realized overlap and replay recruitment.

## Generalized signatures

Define generalized signatures in:

```text
src/cytodend_accessmodel/signatures.py
```

or a companion module that calls the locked signature logic.

### gSIG-A — expected-overlap structural writing

Do expected overlap branches gain more `M_b` than non-overlap branches?

```text
gSIG_A = mean(delta_M_expected_overlap) - mean(delta_M_nonoverlap)
```

### gSIG-B — expected-pair linking gain

Do expected linked trace pairs increase linking more than expected unlinked pairs?

```text
gSIG_B = mean(delta_L_expected_pairs) - mean(delta_L_unlinked_pairs)
```

### gSIG-C — context/allocation separation

Does context or cue-specific recall remain separable?

This may remain architectural and non-diagnostic, as in E018–E020.

### gSIG-D — perturbation specificity

Does damage to expected overlap branches impair linked pairs more than unlinked pairs or single-trace recall?

```text
gSIG_D = linked_pair_damage_drop - unlinked_or_single_trace_damage_drop
```

### gSIG-E — rescue selectivity

Does targeted rescue of expected overlap branches improve linked-pair recovery more than generic or non-overlap rescue?

Use the E019R normalized-recovery convention.

```text
gSIG_E = NR_targeted_expected_overlap - NR_reference
```

## False-linking metric

E021 should add a false-linking metric.

Recommended:

```text
false_linking_rate =
    mean(L_unlinked_pairs_post - L_unlinked_pairs_pre)
    /
    mean(L_expected_linked_pairs_post - L_expected_linked_pairs_pre)
```

Alternative:

```text
specificity_index =
    delta_L_expected_pairs - delta_L_unlinked_pairs
```

Use whichever is more stable, but document the choice.

Important article-facing principle:

```text
A hub motif may produce strong linking but poor specificity.
That is a valid failure/boundary condition, not something to hide.
```
